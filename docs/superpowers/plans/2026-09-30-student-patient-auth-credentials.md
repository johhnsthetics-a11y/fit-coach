# Student and Patient Auth Credentials Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a trainer or nutritionist generate a real Supabase Auth login with a one-time temporary password for their own student/patient, require a personal password at first login, then continue through the existing CoachFit payment funnel.

**Architecture:** An additive migration links `students` to `auth.users` and exposes only current-user bootstrap functions. A protected Edge Function performs privileged Auth creation and first-password replacement. The React app reuses the existing invitation-backed portal internally while adding professional credential sharing and role-aware login routing.

**Tech Stack:** React 18, Vite, JavaScript/JSX, Tailwind CSS, Supabase Auth/PostgreSQL/Edge Functions, Node test runner, PGlite.

**Spec:** `docs/superpowers/specs/2026-09-30-student-patient-auth-credentials-design.md`

## Global Constraints

- Never expose or use `service_role` in the frontend.
- Never store the temporary or personal password in PostgreSQL, local storage, logs, analytics, or user metadata.
- Authorization comes from the authenticated caller and persisted relationships, never a frontend `coachId`.
- Preserve the current invitation portal and Cartpanda financial enforcement during rollout.
- Existing students/patients are converted only when their professional requests credentials.
- No automated email dependency; sharing is copy or WhatsApp.

## Review Focus

- Lost generation response: retry replaces the unused temporary password without creating a second Auth account.
- Duplicate email: no partial Auth/database record and no disclosure of unrelated account details.
- Student refresh: a persisted student session must never load or flash the professional workspace.
- Partial first-password update: portal remains blocked until both Auth password and database flag are complete, with a safe retry.
- Existing professional and invitation logins: both continue working unchanged after role-aware routing is added.
